# M2.12 – Mounts on a running context

- Date: 2026-10-21
- Host: Ubuntu 26.04 LTS, Podman 5.7.0, kernel 7.0.0-38-generic

## Question

Can a host folder be mounted into a running rootless context without
recreating its container (for M5.11: apply mount changes)? Where can it appear,
and what happens to processes using it when it is unmounted?

## Setup

`docs/spikes/setup/live-mounts.sh`: in rootless Podman's user+mount namespace
(`podman unshare`) a per-context directory is made a shared mount point before
the container starts; the container mounts it with `rslave` (koje's flags:
`--userns=keep-id`, `label=disable`, koje's base image). Folders bind-mounted
into that directory later, again inside Podman's namespace, should propagate
into the running container. Test container `koje-spike-mounts`
(`io.koje.test=true`), cleaned up by the script.

## Result

| Check | Result | Notes |
|---|---|---|
| Shared mount point in Podman's namespace, persists across `podman unshare` calls | yes | `shared,slave` (slave of the host, shared inside Podman's namespace) |
| Container sees the directory as a slave mount | yes | `private,slave` |
| Folder mounted while running is visible inside | **yes** | round 1, step 4 |
| Writes from the container land on the host, owned by the user | yes | uid 1000 (keep-id) |
| Read-only folder is read-only inside | round 1 (`bind`, then `remount,ro`): **no**; round 2 (ro bind in a private staging dir, then bound into the shared dir): **yes** | the container's copy is made at the bind; later flag changes do not propagate, a bind copies its source's flags |
| Unmount while a process uses it | `umount`: "target is busy", stays inside; `umount -l`: gone inside, the process keeps running | koje unmounts lazily |
| Folders survive `podman restart` | yes | |
| Folder at its own path (symlink inside the container) | round 2 (home volume as in a context): **yes** | `pwd` shows the own path, `pwd -P` the real one below `/run/koje-live`; round 1 had no writable home |
| Host does not see the Podman-namespace mounts | yes | |

### Round 3: the home as the propagation point

`live-mounts.sh` (round 3): the home volume's directory
(`~/.local/share/containers/storage/volumes/<volume>/_data`) is made a shared
mount point in Podman's namespace and mounted at `$HOME` with `rslave` instead of
the named volume; a folder is bound to `<volume dir>/work/project` while the
container runs.

| Check | Result | Notes |
|---|---|---|
| Volume directory owned by the user on the host | yes | uid 1000 |
| Home in the container: the user's, writable (without `:U`) | **yes** | `1000 755` |
| Folder appears at its own path below `$HOME` | **yes** | `~/work/project` |
| A real mount there, no symlink | **yes** | `pwd -P` and `findmnt` both `/home/…/work/project` |
| Writes from the container land on the host, owned by the user | yes | |
| Rest of the home untouched | yes | |
| Lazy unmount while a process uses it | gone in the container, the process keeps running | |
| Survives `podman restart` | yes | |
| Host's own view unaffected | yes | |

## Conclusion

**Folders can be mounted into a running rootless context without recreating
it**, without root, and – with round 3 – **at their own path as real mounts**:

1. Before the container starts, the home volume's directory is made a shared
   mount point inside rootless Podman's namespace (`podman unshare mount --bind
   D D; mount --make-rshared D`); the container mounts it at `$HOME` with
   `rslave` (same data as the named volume; ownership right without `:U`).
2. `podman unshare mount --bind <folder> D/<path below $HOME>` makes the folder
   appear at that path in the running context; writes land on the host, owned
   by the user; it survives `podman restart`; the host's own view is unaffected.
3. Unmounting: `umount -l` – a process using the folder keeps running.
4. Limits: only folders below `$HOME` (everything else needs a recreate). A
   read-only mount would need the staging trick of round 2 (ro bind in a
   private directory first, then bound in).
5. Rounds 1–2 (a separate shared directory plus symlinks at the own path) work
   too but leave symlinked paths; not pursued.

Not tested: what restarting rootless Podman's pause process (`podman system
migrate`, reboot) does to the shared directory – after a reboot `koje up`
prepares it again before starting the container.
