# M8.87 – Why windows cannot be moved by their title bar

- Date: (to fill in on the host)
- Host: (distribution, kernel, Hyprland version, GPU)

## Question

In the koje session a window can only be moved with Super+drag, even when it
draws its own title bar (GTK header bars, Firefox). Why – and what does
GNOME's behaviour (drag the title bar, a maximized window unmaximizes under
the pointer, top edge maximizes, sides tile) need from Hyprland or koje's
plugin?

Suspects: windows that opened maximized (M8.74 – `FSMODE_MAXIMIZED`), whose
`xdg_toplevel.move` Hyprland ignores; move requests from windows in contexts
(the security context, ADR 0019); hyprbars' own drag handling.

## Setup

Prepared commands – run each and note what happens:

```sh
# 1. Which windows are maximized (fullscreen 1) or floating?
hyprctl clients -j | jq '.[] | {class, floating, fullscreen, fullscreenClient}'

# 2. A host GTK app (not in a context), not maximized: drag its header bar.
gnome-text-editor &   # or any GTK 4 app on the host
#    then: hyprctl dispatch fullscreenstate 0 0   (with it focused)

# 3. The same app maximized: drag its header bar.
#    (Super+Up, or let it open maximized)

# 4. Without koje's auto-maximize: does a new window drag?
hyprctl keyword plugin:koje:auto_maximize 0

# 5. A context's GTK app (koje run <context> gnome-text-editor), not maximized.

# 6. Hyprland's log while dragging (move requests show up with debug logs):
hyprctl keyword debug:disable_logs false
tail -f "$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/hyprland.log" | grep -i -E 'move|drag|interactive'
```
