# M2.8 – Pausing a context with windows

- Date: 2026-10-17
- Host: Ubuntu 26.04 LTS, Podman 5.7.0, Hyprland v0.53.3 nested in GNOME,
  **without** `hyprland-guiutils`

## Question

What does Hyprland do with the windows of a context that `podman pause` freezes:
a "not responding" dialog? Does resuming work? Is it different when the windows
are in the stash (special workspace) first?

## Setup

Context `koje-spike-a` (`run-context.sh a wayland-1`) with several `foot`
windows on the nested Hyprland (`hyprland-nested.conf`), `podman pause` /
`podman unpause koje-spike-a`. Stash: `special:stash` (ALT+H stash, ALT+SHIFT+H
show/hide, ALT+CTRL+H unstash).

## Result

| Check | Result | Notes |
|---|---|---|
| Windows while paused (visible) | frozen, still drawn | clicked and typed into them |
| "Not responding" dialog / marking | none within about a minute | `hyprland-guiutils` not installed – it likely draws that dialog; recheck with it |
| After `podman unpause` | windows react at once; queued keyboard input is processed | |
| Same with the windows in the stash first | as above; stash shows/hides normally while paused | |

## Conclusion

Pausing a context with `podman pause` (cgroup freezer) is safe for its windows:
no data loss, input is queued and delivered on resume. Moving windows to the
stash before pausing (concept "Pausieren") is not technically required but keeps
frozen windows out of the way.

Open: with `hyprland-guiutils` installed (normal setups), does Hyprland show its
"not responding" dialog for frozen windows, and can it be disabled? Recheck
during M2.1. The open question *Paused contexts* is narrowed to that.
