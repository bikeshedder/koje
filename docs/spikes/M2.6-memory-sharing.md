# M2.6 – Memory sharing between contexts

- Date: 2026-10-17
- Host: Ubuntu 26.04 LTS, kernel 7.0.0-38-generic, RAM …, Podman 5.7.0

## Question

Do two contexts from the same base image share library pages (e.g. of the
browser)? Does a context's cgroup memory include its nested containers?

## Setup

Two contexts `koje-spike-a`, `koje-spike-b` from `localhost/koje-spike/base`,
Firefox in each with the same pages open. Baseline: two Firefox profiles in *one*
container (the host's Firefox is a Snap, so it is not a fair comparison).
Measured with `docs/spikes/setup/mem.sh` and `cgroup-mem.sh` after ~1 min idle.

## Result

| Setup | Σ RSS MiB | Σ PSS MiB | Σ shared MiB |
|---|---|---|---|
| Firefox in context a only (b's Firefox closed) – *a restarted in between, not comparable* | 1417.2 | 729.9 | 811.8 |
| Firefox in a and b – context a (12 processes) | 1308.4 | 631.0 | 788.2 |
| Firefox in a and b – context b (12 processes) | 1331.6 | 650.7 | 792.3 |
| Firefox in a and b – sum | 2640.0 | 1281.7 | 1580.5 |
| Baseline: two profiles in a | | | |

Sharing factor for libxul in a: 66.8 / 116.3 = 0.57 (≈ ½ with two instances).
The whole-process comparison above is not usable (a's Firefox was restarted
between runs); the per-library measurement replaces it, and also replaces the
"two profiles in one container" baseline.

Note: "shared" also counts pages shared between the processes of *one* Firefox
(binary, libxul). Cross-context sharing shows as a rise of a's PSS when b's
Firefox is closed. Page cache is charged to the cgroup that first read a page,
so `memory.current` of a and b can differ for the same workload.

| cgroup `memory.current` of koje-spike-a | MiB |
|---|---|
| Firefox running (b's Firefox also running) | 840.2 (anon 525.6, file 286.6, kernel 27.5, shmem 19.2); all in sub-cgroup `/container` |
| b while both run (for comparison) | 799.7 → 838.9 after a Firefox restart (anon 561.9, file 242.8) |
| a after b's Firefox closed | 872.2 (anon 535.1, file 306.0) |
| b after its Firefox closed (no programs left) | 229.4 (anon 0.1, **file 220.9**, kernel 8.3) |
| before the nested container (Firefox running) | 694.7 (anon 469.2) |
| with a nested container holding 500 MiB (`python:3-alpine`, `b'x' * (500 << 20)`) | 1193.8 (anon 893.0) |

Nested containers counted in the context's cgroup: **yes** (+499 MiB). The inner
process sits in `libpod-….scope/container`, the same cgroup as the context's own
programs: with `cgroups = "disabled"` (ADR 0014) dev containers get no cgroup of
their own. (A first attempt with BusyBox `tail` as the hog held no memory.)

Cross-context sharing, measured on `libxul.so` only (`lib-pss.sh`), Firefox in a
left untouched:

| a's libxul mappings | Rss MiB | Pss MiB |
|---|---|---|
| b's Firefox closed | 596.4 | 116.3 |
| b's Firefox running | 596.3 | 66.8 |
| b's Firefox closed again | 596.3 | 116.3 |

**Result: shared.** a's Pss for libxul drops by 43 % while b's Firefox runs and
returns exactly when it closes, with Rss unchanged. The physical pages of the
image's libraries exist once for all contexts using the same image layer.

Observations so far:

- Page cache stays charged to a context after its programs exit (b: 221 MiB
  file pages with no process left). It is reclaimable, but counts in
  `memory.current` – relevant for soft/hard limits (M6).
- First-touch charging: the same workload shows 800–840 MiB in b and 840–870 MiB
  in a.

## Conclusion

- **Shared libraries: yes.** Contexts started from the same image layers share
  the physical pages of its files. With two Firefox instances, a's Pss for
  libxul drops from 116 to 67 MiB and returns when the other one closes. Every
  further context with the same base image saves roughly the size of the
  libraries it uses. This favours one common base image (or common lower
  layers) for all contexts.
- **Nested containers: counted.** A context's `memory.current` includes its dev
  containers, so soft and hard limits (M6) cover the whole context. There is no
  per-dev-container figure, since dev containers get no own cgroup.
- **Page cache is charged to the context that read a file first** and stays
  charged after its programs exit (b: 221 MiB with no program left). It is
  reclaimable, but counts towards `memory.current` and therefore towards limits.
  For the soft-limit warning, M6 should look at `anon` (or `memory.current`
  minus reclaimable file pages), not only at `memory.current`.
