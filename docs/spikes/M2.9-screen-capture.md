# M2.9 – Screen capture permissions

- Date: 2026-10-18
- Host: Ubuntu 26.04 LTS, Hyprland 0.53.3 (real session), Podman 5.7.0

## Question

Can programs in a context be denied direct screen capture (`screencopy`) while
screen sharing through the portal (video calls) keeps working?

Two mechanisms: Hyprland's **permission rules** (match the client's executable
path) and **`security-context-v1`** (koje hands each context a Wayland socket
that marks all its clients as sandboxed).

## Setup

Context a from `run-context.sh`; `grim` in the image; `wl-secure-socket` for the
security context socket.

## Result

| Check | Result | Notes |
|---|---|---|
| Baseline: `grim` on the host / in the context | **both capture the whole screen** | context on the normal socket `wayland-1` |
| Path of a context binary as the host sees it (`/proc/<pid>/exe`) | `/usr/bin/sleep` – the path inside the container | a path rule cannot tell host and context apart |
| Permission rule `/usr/bin/grim, screencopy, deny`: host grim / context grim | not tested | would hit host and context alike (same path) |
| Hyprland offers `wp_security_context_manager_v1` | **yes** | `wl-secure-socket` registered `io.koje` / `io.koje.a` |
| Context on the security-context socket: windows open | | |
| … `grim` in the context | **denied** | "compositor doesn't support the screen capture protocol" – the protocol is not offered to sandboxed clients |
| … screen sharing through the portal from the context | | must still work |
