# M8.65 – What xdph hands to a screen sharing picker

- Date: 2026-10-26
- Host: Ubuntu 26.04 LTS, Hyprland 0.53.3, xdg-desktop-portal-hyprland 1.3.11, koje session (`XDG_CURRENT_DESKTOP=koje:GNOME`)

## Question

Can koje replace xdph's screen sharing picker (M8.66)? What does xdph pass to
a `custom_picker_binary`, what reply does it expect, and does anything tell the
picker which app or context asked?

## Setup

`~/.config/hypr/xdph.conf`:

```
screencopy {
    custom_picker_binary = /home/<user>/.local/bin/xdph-picker-probe
}
```

The probe logs its arguments and environment, runs the stock
`/usr/bin/hyprland-share-picker` with the same arguments and passes its stdout
and exit code on:

```sh
#!/bin/sh
log="$HOME/xdph-picker-probe.log"
picker="$(command -v hyprland-share-picker || echo /usr/bin/hyprland-share-picker)"
{ echo "=== $(date '+%F %T')"; echo "args: $*"; env | sort; } >> "$log"
out="$("$picker" "$@" 2>>"$log")"; code=$?
{ echo "--- picker stdout (exit $code)"; printf '%s\n' "$out"; } >> "$log"
printf '%s\n' "$out"; exit $code
```

Then `systemctl --user restart xdg-desktop-portal-hyprland` and shares from
Firefox (gUM test page).

## Result

- **Arguments:** none.
- **Environment:** the service's own (systemd user unit: session variables,
  `HYPRLAND_INSTANCE_SIGNATURE`, `WAYLAND_DISPLAY`, `QT_QPA_PLATFORM=wayland`)
  plus `XDPH_WINDOW_SHARING_LIST`. Nothing names the requesting app, its PID or
  the portal request.
- **Window list:** entries one after another, each
  `<handle>[HC>]<class>[HT>]<title>[HE>]<address>[HA>]`:

  ```
  852087840[HC>]firefox_firefox[HT>]gUM Test Page — Mozilla Firefox[HE>]95409315344256[HA>]
  852332432[HC>]com.microsoft.VSCode[HT>]Dev Container: koje - workspace[HE>]95409315570416[HA>]
  ```

  - `<handle>` is the low 32 bits of the foreign toplevel's Wayland resource
    pointer (xdph's own ID), used in the reply.
  - `<address>` is Hyprland's window address in decimal (from Hyprland's
    toplevel mapping protocol; `0` without it): 95409315344256 = 0x56c636596f80,
    which `hyprctl clients` shows for that Firefox window. kojed can map each
    entry to its context.
  - Class and title are sanitized: `'`, `"`, `$` and backticks become spaces.
  - The list holds every window xdph knows, whoever asks.
- **Reply** (stdout, exit 0): `[SELECTION]<flags>/<kind>:<value>`, seen
  `[SELECTION]/window:852087840` (the handle) and `[SELECTION]/screen:DP-3` (the
  output's name). Flags were empty – the restore checkbox was not ticked.
- Sharing worked through the probe.

From xdph 1.3.11's source (`src/shared/ScreencopyShared.cpp`,
`promptForScreencopySelection`), for what the runs did not show:

- The picker gets `--allow-token` only when `screencopy:allow_token_by_default`
  is set; the picker's `r` flag grants a restore token either way.
- `screen:<output>` drops the last character of the value – the reply needs a
  trailing newline. `window:<handle>` is parsed as a decimal number;
  `region:<output>@<x>,<y>,<w>,<h>` in whole numbers.
- No explicit cancel: output without `[SELECTION]` returns an empty selection
  and the share is refused (Firefox: `NotAllowedError`).
- xdph sets `WAYLAND_DISPLAY`, `QT_QPA_PLATFORM=wayland`, `XCURSOR_SIZE`,
  `HYPRLAND_INSTANCE_SIGNATURE` and `XDPH_WINDOW_SHARING_LIST` for the picker,
  nothing about the request.

## Conclusion

- A koje picker is possible without touching xdph: it reads
  `XDPH_WINDOW_SHARING_LIST`, maps the addresses to contexts through kojed and
  prints `[SELECTION]<flags>/window:<handle>`, `/screen:<output>` or
  `/region:…` with a trailing newline, or nothing to cancel.
- xdph does not tell the picker who asked. Pre-selecting the asking context
  (M8.66) can only be a guess, e.g. the focused window's context.
- Thumbnails can reuse the overview's capture (M8.67), by window address.
